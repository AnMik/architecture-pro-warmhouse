### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут управлять температурой отопления в доме.
- Система позволяет выставлять необходимую температуру в доме.
- Система поддерживает подключение новых установок с помощью специалиста.

**Мониторинг температуры:**

- Пользователи могут проверять температуру на датчиках.
- Система поддерживает запросы к датчикам для проверки текущей тмпературы.

### 2. Анализ архитектуры монолитного приложения

Архитектура приложения представляет из себя монолит на Go с СУБД Postgres. Всё синхронно. Никаких асинхронных вызовов, микросервисов и реактивного взаимодействия в системе нет. Всё управление идёт от сервера к датчику. Данные о температуре также получаются через запрос от сервера к датчику.

### 3. Определение доменов и границы контекстов

В нынешней версии приложения существует только один домен "Управление умным домом".

### **4. Проблемы монолитного решения**

1. Трудности с маштабированием нагрузок на чтение данных с датчиков и регулировку температуры.
2. Высокий риск выхода из строя всей системы из-за высокой связности компонентов системы.
3. Сложности с разработкой:
3.1. Замедление параллельной разработки из-за изменений в общей кодовой базе.
3.2. Замедление релизов из-за более объемного тестирования.
3.3. Высокий риск косвенных ошибок из-за выссокой связности компонентов системы.
4. Отсутствие гибкости в части добавления новой фунциональности (для подключения новых типов датчиков)

# Задание 3. Разработка ER-диаграммы

1. Сущности:
	1. Пользователь (User)
	2. Дом (House)
	3. Помещение (Room)
	4. Устройство (Device)
	5. Состояние устройства (DeviceState)
	6. Правило (Rule)
	7. Триггеры правил (RuleTrigger)

2. Атрибуты:
	1. Пользователь (User):
		1. id - уникальный идентификатор
    	2. email - эл. почта
    	3. phone - телефон
    	4. password_hash - хэш пароля
    	5. first_name - имя
    	6. last_name - фамилия
    	7. created_at - дата создания
	2. Дом (House):
		1. id - уникальный идентификатор
    	2. user_id - владелец (внешний ключ к таблице User)
		3. name - название
		4. address - адрес
		5. timezone - таймзона
	3. Помещение (Room):
		1. id - уникальный идентификатор
		2. house_id - квартира (внешний ключ к таблице House)
		3. name - название
		4. room_type - тип помещения
	4. Устройство (Device):
		1. id - уникальный идентификатор
		2. name - название
		3. device_type - тип
		4. room_id - идентификатор комнаты (внешний ключ к таблице Room)
		5. serial_number - серийный номер
    	6. manufacturer - производитель
	5. Состояние устройства (DeviceState):
		1. id - уникальный идентификатор
		2. device_id - идентификатор устройства (внешний ключ к таблице Device)
		3. enabled - включено/выключено
		4. power_level - уровень мощности
		5. mode - режим работы
		6. active_rule_id - идентификатор активного правила (внешний ключ к таблице Rule)
    	7. updated_at - время последнего обновления
	6. Правило устройства (Rule):
		1. id - уникальный идентификатор
    	2. name - название
		3. device_id - идентификатор устройства (внешний ключ к таблице Device)
    	4. trigger_ids - идентификаторы триггеров правил
	7. Триггеры правил (RuleTrigger):
		1. id - уникальный идентификатор
		2. name - название
		3. type - тип срабатывания
		4. conditions - условия срабатывания
		5. action - действие

3. Связи:
	1. Пользователь - Дом: один пользователь может иметь доступ к нескольким домам, но каждый дом связан только с одним пользователем.
	2. Дом — Помещение: один дом может содержать несколько помещений, и каждое помещение принадлежит только одному дому.
	3. Помещение — Устройство: одно помещение может содержать несколько устройств, и каждое устройство принадлежит только одному помещению.
	4. Устройство — Состояние устройства: одно устройство может имет только одно состояние, и одно состояние может принадлежать только одному устройству.
	5. Состояние устройства - Правило: одно состояние устройства может имет только одно активное правило, и одно правило может принадлежать только одному состоянию.
	6. Правило - Триггеры правил: одно правило может иметь несколько триггеров, и один триггер может принадлежать нескольким правилам.

# Задание 4. Создание и документирование API

### 1. Тип API

В потенциальной системе будет использоваться два типа коммуникаций: синхронное и асинхронное.
Синхронная коммуникация используется для настроек системы (управления пользователями, устройствами, настройками и тд), потому что она производится пользователем через UI.
Асинхронная коммуникация используется для отправки управляющих команд устройствам и получения событий телеметрии от устройств, потому что коммуникация с устройствами может быть нестабильной, и важно уметь обрабатывать ситуации временной недоступности.
